**Время:** 1-2 недели

#### Что нужно сделать

1. **Создать тестовый стенд**

   - Настроить логирование всех этапов подключения
   - Создать чек-лист тестовых сценариев

2. **Тестовые сценарии**
   - [ ] Два устройства в одной WiFi сети (mDNS)
   - [ ] Два устройства в разных WiFi сетях (DHT)

   - [ ] Подключение через bootstrap peers
   - [ ] STUN для определения внешнего IP
   - [ ] Соединение с мобильным интернетом (4G/5G)
   - [ ] Соединение через разные провайдеры

3. **Диагностические инструменты**
   - [ ] Команда `p2p status` — показать текущее состояние сети
   - [ ] Лог всех попыток подключения с причинами失败
   - [ ] Визуальный индикатор типа подключения (direct/relay/dht)
   - [ ] Тест скорости соединения между пирами

4. **Файл логирования**
   - [ ] Заменить `fmt.Println` на структурированный логгер (zap/slog)
   - [ ] Уровни: debug, info, warn, error
   - [ ] Ротация логов (файл + консоль)
   - [ ] Отдельный лог для P2P событий

#### Технические детали

Текущая архитектура уже поддерживает:
- DHT (глобальный поиск)
- Relay (обход NAT)
- STUN (определение внешнего IP)

Проблема скорее всего в:
- Настройках firewall/антивируса
- Отсутствии работающих bootstrap peers
- Неправильной конфигурации relay

#### Риски
- Некоторые NAT типы (symmetric) могут блокировать прямое соединение
- Требуется минимум 2 физических устройства для тестов

### 2. 💬 Групповые чаты

**Сложность:** ⭐⭐⭐⭐⭐ (высокая)
**Время:** 3-5 недель

#### Что нужно сделать

1. **Протокол группового чата** (`/projectt/groupchat/1.0.0`)
   - [ ] Структура сообщения с group_id
   - [ ] Управление участниками (invite/kick/leave)
   - [ ] Метаданные группы (название, описание, аватар)
   - [ ] Роли (admin/moderator/member)

2. **Архитектура распространения сообщений**

   **Вариант A: PubSub (рекомендуется)**
   - Использовать `go-libp2p-pubsub` (уже в зависимостях!)
   - Каждый групповой чат = отдельный topic
   - Сообщения broadcast всем подписчикам
   - Плюсы: нативно в libp2p, mesh сеть
   - Минусы: все участники должны быть онлайн

   **Вариант B: Store-and-Forward**
   - Каждый участник хранит историю
   - При подключении синхронизирует недостающие
   - Плюсы: оффлайн доступ
   - Минусы: сложная синхронизация

   **Рекомендация:** Гибрид — PubSub для онлайн + sync при подключении

3. **База данных**
   - [ ] Таблица `group_chats` (id, name, creator_peer_id, created_at)
   - [ ] Таблица `group_members` (group_id, peer_id, role, joined_at)
   - [ ] Таблица `group_messages` (id, group_id, from_peer_id, content, timestamp)
   - [ ] Миграция для новых таблиц

4. **UI для групповых чатов**
   - [ ] Список групповых чатов в левой панели
   - [ ] Кнопка "Создать группу"
   - [ ] Окно приглашения участников (по PeerID)
   - [ ] Отображение имени отправителя в сообщении
   - [ ] Аватары участников
   - [ ] Информация о группе (правая панель)
   - [ ] Управление участниками (для админа)

5. **Синхронизация истории**
   - [ ] При подключении к группе — запрос последних N сообщений
   - [ ] Vector clocks для определения порядка
   - [ ] Разрешение конфликтов при рассинхроне

6. **Безопасность**
   - [ ] Шифрование сообщений группы (общий ключ)
   - [ ] Верификация участников
   - [ ] Защита от спама (лимиты)
   - [ ] Исключение участников = отзыв ключа

### 4. 🪙 Криптовалюта для вознаграждения пользователей

**Сложность:** ⭐⭐⭐⭐⭐⭐ (очень высокая)

#### Что нужно сделать

##### 4.1. Создание собственной криптовалюты

**Вариант A: Токен на существующем блокчейне (рекомендуется)**
- Создать токен на базе Ethereum (ERC-20) или TON
- Плюсы: готовая инфраструктура, кошельки, биржи
- Минусы: зависимость от внешней сети, комиссии

**Вариант B: Собственный блокчейн**
- Написать свой консенсус (PoS/PoW)
- Плюсы: полный контроль
- Минусы: огромная сложность, безопасность

**Вариант C: Внутренняя система баллов (рекомендуется для начала)**
- Не блокчейн, а внутренняя учётная система
- Плюсы: быстро, не нужен внешний блокчейн
- Минусы: не "настоящая" крипта, нельзя вывести

**Рекомендация:** Начать с Варианта C, потом мигрировать на A

##### 4.2. Внутренняя система баллов (MVP)

1. **Модель данных**
   - [ ] Таблица `wallets` (peer_id, balance, created_at)
   - [ ] Таблица `transactions` (id, from_peer, to_peer, amount, type, timestamp)
   - [ ] Таблица `rewards_log` (id, peer_id, reward_type, amount, timestamp, details)

2. **Типы вознаграждений**

   | Действие | Награда | Описание |
   |----------|---------|----------|
   | Хранение данных | X/час | За каждый ГБ данных других пользователей |
   | Передача данных | X/МБ | За ретрансляцию чужих сообщений/файлов |
   | Обмен профилями | X | За передачу списка контактов новому пиру |
   | Раздача файлов | X/запрос | За ответ на запрос файла из библиотеки |
   | Хранение библиотеки | X/элемент | За хранение общих элементов |
   | Аптайм | X/день | Бонус за время онлайн |

3. **Механизм подсчёта**

   ```go
   type RewardEngine struct {
       db         *sql.DB
       metrics    *MetricsCollector
       config     *RewardConfig
   }

   // Пример: начисление за хранение
   func (r *RewardEngine) CalculateStorageReward(peerID string, bytesStored int64, hours int) int64 {
       gbStored := float64(bytesStored) / 1e9
       rate := r.config.StorageRatePerGBPerHour // например, 0.01 токенов
       return int64(gbStored * rate * float64(hours) * 1000) // в миллитокенах
   }

   // Пример: начисление за передачу
   func (r *RewardEngine) CalculateTransferReward(peerID string, bytesTransferred int64) int64 {
       mbTransferred := float64(bytesTransferred) / 1e6
       rate := r.config.TransferRatePerMB // например, 0.005 токенов
       return int64(mbTransferred * rate * 1000)
   }
   ```

4. **Доказательство работы (Proof of Service)**

   Проблема: как проверить, что пользователь действительно хранит/передаёт данные?

   **Решения:**
   - [ ] Challenge-response: случайная проверка хеша хранимого файла
   - [ ] Подписанные квитанции: получатель подписывает факт получения
   - [ ] Web of Trust: пиры оценивают друг друга
   - [ ] Логирование + консенсус: несколько пиров подтверждают действие

   ```go
   // Квитанция о передаче
   type TransferReceipt struct {
       TransferID    string    `json:"transfer_id"`
       FromPeer      string    `json:"from_peer"`
       ToPeer        string    `json:"to_peer"`
       RelayPeer     string    `json:"relay_peer"`
       Bytes         int64     `json:"bytes"`
       Timestamp     int64     `json:"timestamp"`
       RecipientSig  []byte    `json:"recipient_sig"`  // Подпись получателя
   }
   ```

## ⚠️ Ключевые риски

1. **Fyne ограничения**
   - UI фреймворк может не поддерживать все desired элементы Telegram-style
   - **Митигация:** Проверить возможности Fyne до начала редизайна, рассмотреть альтернативы (Wails, Fyne + custom canvas)

2. **libp2p PubSub для групповых чатов**
   - PubSub требует хорошего покрытия сети
   - **Митигация:** Использовать гибридный подход (PubSub + direct messages)

3. **Экономика криптовалюты**
   - Баланс вознаграждений сложно настроить
   - **Митигация:** Начать с внутренней системы, собирать метрики, корректировать

4. **Безопасность**
   - Криптовалюта привлекает злоумышленников
   - **Митигация:** Консервативные лимиты, репутационная система, аудит

5. **Тестирование P2P**
   - Требует физических устройств в разных сетях
   - **Митигация:** Использовать облачные VM, попросить друзей помочь
